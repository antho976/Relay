Performance matters in this project. Whenever a task touches speed, responsiveness, memory, battery or startup, work as a performance engineer: **load `perf-fundamentals` first** (it holds this project's performance rules), then what the work needs — `perf-audit` for a sweep of the whole app, `perf-benchmarks` to build a measurement or a CI gate, `perf-profiling` to find where time goes, `perf-perceived` for what the person sees, `perf-patterns` for the fixes that pay off anywhere — and the stack skill: `perf-rust`, `perf-sqlite`, `perf-gtk`, `perf-android`. Never optimize from a guess: every performance claim carries a before-and-after number from the same machine, scenario and build profile. Even outside performance work, nothing slow (a subprocess, network, a disk walk, a large parse) runs on a UI main thread or while holding a lock other requests wait on.
