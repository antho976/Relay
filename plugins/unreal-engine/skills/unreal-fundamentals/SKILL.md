# Unreal Engine fundamentals

Read this first in any Unreal project. It tells you what the files are, which ones you may edit
as text, how the engine's object model works, and where to look when you are unsure. Deeper
material:

- `reference/project-layout.md` - every top-level folder and file, `.uproject` / `.uplugin` /
  `.Target.cs` / `.Build.cs` anatomy, module types and loading phases. Read it before adding a
  module, a plugin, a target, or editing `.uproject`.
- `reference/naming-conventions.md` - C++ type prefixes, asset prefixes and suffixes, folder
  conventions. Read it before creating any class or asset.

Sibling skills: `unreal-cpp` (writing C++), `unreal-blueprints` (Blueprint assets, data assets,
Python editor scripting of Blueprints), `unreal-gameplay-framework` (GameMode, Pawn, input,
camera, spawning, saving, travel), `unreal-editor-automation` (driving the editor through the
MCP tools and Python), `unreal-build-packaging` (builds, cooking, packaging),
`unreal-multiplayer`, `unreal-ui-umg`, `unreal-animation`, `unreal-ai`, `unreal-gas`,
`unreal-materials-vfx`, `unreal-level-environment`, `unreal-performance`, `unreal-game-design`.

## First moves in an unfamiliar project

1. Run `ue_project_info`. Note the project name, `EngineAssociation` (engine version or a GUID
   for a source build), modules, enabled plugins and targets.
2. Run `ue_setup_check` if you will need the live editor (Python, asset edits).
3. Read `Source/<Project>/<Project>.Build.cs` and the `*.Target.cs` files, `Config/DefaultEngine.ini`
   and `Config/DefaultGame.ini`. They tell you dependencies, the default maps and GameMode.
4. Look at existing classes before adding new ones; match their naming, folder layout
   (`Public/`/`Private/` or flat) and style.
5. Search assets with `ue_search_assets` rather than guessing paths.

## What you may edit as text, and what you may not

| Kind | Examples | How to change |
|---|---|---|
| Text, editable | `.h`, `.cpp`, `.Build.cs`, `.Target.cs`, `.uproject`, `.uplugin`, `Config/*.ini`, `.py` | Edit directly, then build / restart editor as needed |
| Binary, editor only | `.uasset`, `.umap`, `__ExternalActors__/**.uasset` | `ue_python` (editor scripting), `ue_call`, `ue_property`, or step-by-step instructions for the human |
| Generated, never edit | `Intermediate/`, `Binaries/`, `Saved/`, `DerivedDataCache/`, `*.generated.h`, `*.gen.cpp`, `.sln`/`.vcxproj` | Regenerated by UBT/UHT/editor. Do not delete unless the human asks; explain instead |

Never hand-edit `.uasset`/`.umap`. After editor changes, save with
`unreal.EditorAssetLibrary.save_asset(path)` or `unreal.EditorLoadingAndSavingUtils.save_dirty_packages(True, True)`
and tell the human which assets changed.

## Modules and targets (short version)

- A **module** is a unit of C++ compilation: a folder with `<Name>.Build.cs` plus sources. Game
  code lives in one or more modules under `Source/`; the primary module is usually named after
  the project.
- A **target** (`<Name>.Target.cs`) is a build output: `Game`, `Editor`, `Client`, `Server`, or
  `Program`. A typical project has `<Project>.Target.cs` and `<Project>Editor.Target.cs`.
  `ue_build` defaults to `<Project>Editor`.
- Every module must be listed in `.uproject` (`Modules` array, with `Type` and `LoadingPhase`) and
  in a target's `ExtraModuleNames` (or be depended on by one that is).
- Module dependencies are declared in `.Build.cs`. A linker error `LNK2019 unresolved external
  symbol` on an engine class almost always means a missing entry in
  `PublicDependencyModuleNames`/`PrivateDependencyModuleNames`. Find the owning module by the
  path of the class's header in engine source (`Engine/Source/Runtime/<Module>/...`) or the
  class's API page ("Module: ...").
- Editor-only code (anything that includes `UnrealEd`, `Editor.h`, asset factories, detail
  customizations) belongs in a separate module of `Type: "Editor"`. A runtime module must not
  depend on an editor module or the game will fail to package. Inside runtime modules, guard
  editor-only code with `#if WITH_EDITOR` / `#if WITH_EDITORONLY_DATA`.

Details, templates and the full module type / loading phase list: `reference/project-layout.md`.

## The UObject system

Unreal adds reflection to C++ with macros that the **Unreal Header Tool (UHT)** parses before the
compiler runs. UHT writes `<File>.generated.h` and `<File>.gen.cpp` into `Intermediate/`.

```cpp
// MyItem.h
#pragma once

#include "CoreMinimal.h"
#include "UObject/Object.h"
#include "MyItem.generated.h"          // must be the LAST include

UENUM(BlueprintType)
enum class EItemRarity : uint8 { Common, Rare, Epic };

USTRUCT(BlueprintType)
struct FItemStats
{
    GENERATED_BODY()

    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Stats")
    float Weight = 1.f;
};

UCLASS(BlueprintType, Blueprintable)
class MYGAME_API UMyItem : public UObject
{
    GENERATED_BODY()

public:
    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Item")
    EItemRarity Rarity = EItemRarity::Common;

    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Item")
    FItemStats Stats;

    UFUNCTION(BlueprintCallable, Category = "Item")
    float GetValue() const;
};
```

Rules:
- `UCLASS` types derive from `UObject` (prefix `U`) or `AActor` (prefix `A`). `USTRUCT` types are
  plain value types (prefix `F`), not garbage collected, no UFUNCTIONs callable from Blueprint on
  them. `UENUM` should be `enum class ... : uint8` for Blueprint exposure.
- `GENERATED_BODY()` goes first in the class/struct body. The `.generated.h` include is the last
  include in the header. `MYGAME_API` (module name uppercased + `_API`) exports the class from the
  module; omit it only if nothing outside the module uses the class.
- Only reflected members (UPROPERTY/UFUNCTION) are visible to Blueprint, serialization,
  replication, the Details panel, Python and Remote Control.
- UObjects are never created with `new`. Use `NewObject<T>(Outer)`, `CreateDefaultSubobject<T>(Name)`
  (constructor only), or `World->SpawnActor<T>()` for actors.
- Changing a reflected header (adding a UPROPERTY/UFUNCTION/UCLASS) requires a full build with the
  editor closed; Live Coding does not handle it reliably. See `unreal-cpp`.

### Class Default Object (CDO)

Every `UClass` has one default instance, the **CDO**, built by running the C++ constructor once at
startup. New instances copy their defaults from it, and Blueprint subclasses store their
overridden defaults on their own CDO. Consequences:
- Constructors run for the CDO, in the editor, with no world. Only set defaults and create
  subobjects there. Put gameplay logic in `BeginPlay` (actors) or an explicit init function.
- `GetDefault<UMyClass>()` reads the CDO; `GetMutableDefault<UMyClass>()` writes it (used for
  config/settings classes). In Python: `unreal.get_default_object(cls)`.
- Changing a Blueprint's defaults from a script means editing the generated class's CDO (see
  `unreal-blueprints`).

### Garbage collection and references

UObjects are garbage collected by reachability. The GC only sees references it knows about:
- `UPROPERTY()` members (including in `TArray`, `TMap`, `TSet`, and in USTRUCTs held by UPROPERTY).
- Objects added to the root set (`AddToRoot()`), rarely appropriate.
- References reported by `AddReferencedObjects` or held by an `FGCObject` / `TStrongObjectPtr`
  (for non-UObject owners).

A raw `UObject*` member without `UPROPERTY()` is invisible to GC: the object can be collected
and the pointer dangles. This is the single most common UE crash in agent-written code.

| Pointer | Use for | Keeps alive? |
|---|---|---|
| `TObjectPtr<T>` in a `UPROPERTY` | Default for UObject members in UE5 headers | Yes (as UPROPERTY) |
| raw `T*` | Function parameters and locals | No |
| `TWeakObjectPtr<T>` | Observing an object you do not own; lambdas and timers capturing UObjects | No; check `IsValid()`/`Get()` |
| `TSoftObjectPtr<T>` / `TSoftClassPtr<T>` | Referencing an asset that may not be loaded (path-based) | No; load on demand |
| `TSubclassOf<T>` | A class reference restricted to T and subclasses (hard reference) | Yes if UPROPERTY |
| `TStrongObjectPtr<T>` | Holding a UObject from non-UObject code | Yes |
| `TSharedPtr`/`TUniquePtr` | Non-UObject types only | n/a |

Actors are destroyed explicitly with `Destroy()`; after that `IsValid(Actor)` returns false and
the memory is reclaimed later. Always test UObject pointers with `IsValid(Ptr)` (null and
pending-kill check), not just `Ptr != nullptr`. `MarkPendingKill` was replaced by
`MarkAsGarbage` in UE5; you rarely need either.

## Actors, Components, Worlds, Levels

- **UWorld**: the running game (or editor) world. Holds levels, actors, the timer manager,
  subsystems. Get it with `GetWorld()` from actors/components. In PIE the editor world and the
  PIE world are different objects.
- **ULevel**: a collection of actors saved in a map. A world has a persistent level plus
  optionally streamed sublevels, or uses **World Partition** (UE5 default for new open-world
  maps), where actors are saved one file per actor under `Content/__ExternalActors__/` and
  streamed by grid cells. See `unreal-gameplay-framework`.
- **AActor**: anything placeable or spawnable in a world. Has a transform only via its
  `RootComponent`. Lifecycle: see `unreal-gameplay-framework` `reference/actor-lifecycle.md`.
- **UActorComponent**: reusable behavior attached to an actor (no transform).
  **USceneComponent**: has a transform and can attach to other scene components.
  **UPrimitiveComponent**: renders and/or collides (meshes, shapes).
- Composition over inheritance: prefer adding a component to growing a deep actor hierarchy.

## Packages, assets and paths

- A **package** is one `.uasset`/`.umap` file. Usually it contains one main **asset** of the same name.
- Mount points: `/Game/` maps to `Content/`, `/<PluginName>/` maps to a content plugin's
  `Content/`, `/Engine/` to engine content, `/Script/<Module>` to native classes.
- Paths:
  - Package path: `/Game/Characters/Hero/SK_Hero`
  - Object path: `/Game/Characters/Hero/SK_Hero.SK_Hero`
  - Blueprint generated class: `/Game/Blueprints/BP_Door.BP_Door_C`
  - Native class: `/Script/Engine.StaticMeshActor`, `/Script/MyGame.MyItem` (no `U`/`A` prefix)
  - Actor in a level: `/Game/Maps/L_Test.L_Test:PersistentLevel.BP_Door_C_2`
- Renaming or moving an asset in the editor leaves **redirectors** behind. Move/rename only via the
  editor (`unreal.EditorAssetLibrary.rename_asset`), then fix up redirectors (Content Browser >
  right-click folder > Fix Up Redirectors). Never move `.uasset` files with `git mv` or the shell;
  references break.

### Hard vs soft references

- **Hard**: `UPROPERTY` of `TObjectPtr<UStaticMesh>`, `TSubclassOf<AActor>`, a Blueprint variable of
  object type, a cast node to a Blueprint class. Loading the owner loads the target, recursively.
  Easy to use; can pull huge chains of assets into memory.
- **Soft**: `TSoftObjectPtr<T>`, `TSoftClassPtr<T>`, `FSoftObjectPath`. Stores a path; you load
  when needed.

```cpp
UPROPERTY(EditDefaultsOnly, Category = "Visual")
TSoftObjectPtr<UStaticMesh> MeshAsset;

// synchronous (hitches; fine in editor tools, small assets, or load screens)
UStaticMesh* Mesh = MeshAsset.LoadSynchronous();

// asynchronous (needs "Engine/AssetManager.h" and "Engine/StreamableManager.h")
UAssetManager::GetStreamableManager().RequestAsyncLoad(
    MeshAsset.ToSoftObjectPath(),
    FStreamableDelegate::CreateWeakLambda(this, [this]() { /* MeshAsset.Get() is loaded now */ }));
```

Use hard references for things always needed together (a character's own mesh); use soft for
optional or large content (all weapon meshes in a catalog, level lists, UI icons). Inspect with
the editor's Reference Viewer and Size Map (right-click asset).

## Config (.ini) hierarchy

Settings are layered; later layers override earlier ones:

1. `Engine/Config/Base*.ini` (engine defaults, never edit)
2. `Engine/Config/<Platform>/...`
3. `<Project>/Config/Default*.ini` (**the project's text settings; edit these**)
4. `<Project>/Config/<Platform>/<Platform>*.ini` (platform overrides)
5. `<Project>/Saved/Config/<PlatformEditor-or-Platform>/*.ini` (per-user, generated; do not commit)

Main project files: `DefaultEngine.ini` (rendering, maps and modes, physics, GameMapsSettings),
`DefaultGame.ini` (project info, Asset Manager, packaging), `DefaultInput.ini` (input classes and
legacy bindings), `DefaultEditor.ini`, `DefaultEditorPerProjectUserSettings.ini`, `DefaultScalability.ini`.

Syntax:
```ini
[/Script/EngineSettings.GameMapsSettings]
GameDefaultMap=/Game/Maps/L_MainMenu.L_MainMenu
EditorStartupMap=/Game/Maps/L_Test.L_Test
GlobalDefaultGameMode=/Script/MyGame.MyGameMode

[/Script/Engine.AssetManagerSettings]
+PrimaryAssetTypesToScan=(PrimaryAssetType="Map",AssetBaseClass=/Script/Engine.World,bHasBlueprintClasses=False,bIsEditorOnly=True,Directories=((Path="/Game/Maps")))
```
- Section name is `/Script/<Module>.<ClassWithoutPrefix>` for class-backed settings.
- `+Key=` appends to an array (skips exact duplicates), `.Key=` appends allowing duplicates,
  `-Key=` removes a matching entry, `!Key=ClearArray` clears the array. Plain `Key=` sets a scalar.
- A C++ class declared `UCLASS(config=Game)` with `UPROPERTY(config)` members reads them from
  `[/Script/MyGame.MyClass]` in the Game config. `UDeveloperSettings` subclasses appear
  automatically in Project Settings.
- Most Project Settings changes made in the editor are written to `Config/Default*.ini`, so they
  are diffable. Prefer editing the `.ini` directly when you know the key; otherwise make the change
  in the editor (or ask the human) and inspect the diff to learn the key. Many settings are read
  only at startup: tell the human to restart the editor.

## Plugins

A plugin is a folder with `<Name>.uplugin` plus optional `Source/`, `Content/`, `Config/`,
`Resources/`. Project plugins live in `<Project>/Plugins/`; engine plugins in `Engine/Plugins/`.
Enable a plugin by adding `{"Name": "X", "Enabled": true}` to the `.uproject` `Plugins` array
(or Edit > Plugins in the editor, which writes the same thing). If C++ uses a plugin's module,
also add the module to `.Build.cs`. See `reference/project-layout.md` for a `.uplugin` template.

## Naming conventions (short version)

C++ prefixes: `A` actors, `U` other UObjects/components, `F` structs and plain classes, `E` enums,
`I` interfaces, `T` templates, `S` Slate widgets, `b` for bool members (`bIsDead`). Types are
PascalCase, no underscores. Assets: `BP_` Blueprint, `SM_` static mesh, `SK_` skeletal mesh,
`T_` texture, `M_` material, `MI_` material instance, `WBP_` widget, `ABP_` anim Blueprint,
`DA_` data asset, `DT_` data table, `IA_`/`IMC_` input, `L_` or `Lvl_` maps... Always follow the
project's existing convention if it differs. Full tables: `reference/naming-conventions.md`.

## Where to look when unsure

1. The project's own code and config (grep the repo).
2. Engine source headers: the engine directory from `EngineAssociation` (launcher installs:
   `.../UE_5.x/Engine/Source/`). Grep for the class or `UFUNCTION` name; the header shows the real
   signature, specifiers and the owning module (folder under `Runtime/`, `Editor/`, `Developer/`,
   or `Plugins/.../Source/`).
3. Python API in the running editor: `ue_python` with `help(unreal.ClassName)`,
   `dir(unreal.ClassName)`, `hasattr(unreal, "Name")`. Python names are snake_case versions of
   C++ names with the `U`/`A`/`F` prefix dropped (`UEditorAssetLibrary::LoadAsset` becomes
   `unreal.EditorAssetLibrary.load_asset`).
4. The log: `ue_log` with `filter: "Error|Warning"`; UHT and cook errors name the file and line.
5. Epic's documentation (dev.epicgames.com/documentation) for concepts; the header is the source
   of truth for signatures in the installed version.

Do not invent class names, functions, specifiers or console variables. If you cannot find it in
source or via `help()`, say so and propose an alternative.

## Common pitfalls

- Raw `UObject*` members without `UPROPERTY()` - dangling pointers after GC.
- Gameplay logic in constructors - runs on the CDO with no world; `GetWorld()` is null.
- `.generated.h` not the last include, or missing `GENERATED_BODY()` - UHT errors.
- Forgetting to add a module to `.Build.cs` - linker errors.
- Editor module code in a runtime module - packaging fails.
- Moving assets outside the editor - broken references.
- Editing `Saved/Config` instead of `Config/` - change is per-user and lost.
- Assuming every actor in a World Partition map is loaded.

## Verify your work

- [ ] `ue_project_info` shows every new module and plugin; `.uproject` is valid JSON.
- [ ] `ue_build` succeeds (editor closed) for `<Project>Editor`; for runtime modules, a Game target
      build also succeeds when packaging matters.
- [ ] `ue_log` after editor start shows no new `Error` lines from your module or assets.
- [ ] New assets and classes follow `reference/naming-conventions.md` and the project's folders.
- [ ] Every editor change was saved and reported to the human by asset path.
