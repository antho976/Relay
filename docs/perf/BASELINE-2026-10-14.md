# Relay performance baseline — 2026-10-14

The third full reading: every bus op, the non-op paths, the engine process at rest and under load,
memory over a soak, the CLI, and — new — the GTK client page by page and two measurements against
the real store on the measuring machine. Numbers are from `runs/2026-10-14/` (engine JSON and
`report.md`; the client's in `native/`). Compared with `runs/2026-10-07/` by
`scripts/perf/compare.py`. Taken with the Performance plugin's `perf-audit` method.

In one paragraph: the paths a person feels are still fast — a keystroke is 1 µs in process and
12 µs through the socket, the session list 14 µs, the board 290 µs, engine start 4.7 ms, and the
lock invariant holds where the harness tests it (`session.list` 62 µs *during* an overlap scan).
What stands out is new since the last reading: **`project.remove` now backs up the whole store
while holding the store lock** (142–453 ms on the real 260 MB store, every other request waits);
**the store is 260 MB, 85 % of it audit rows written by agents' hooks** on every tool call and
never pruned; and **six GTK pages repaint ~60 times a second while nothing changes**. The heap
growth seen in the soak is a cache filling to its cap, not a leak.

## Machine and method

AMD Ryzen 7 9800X3D (8 cores, 16 threads), 30.5 GiB, NVMe, CachyOS kernel 7.2.9-2, governor
`performance`, boost on; rustc 1.99.0; **dev profile** (`opt-level` 1 workspace, 3 dependencies —
what `run.sh` launches); GTK 4.24.1 for the client. `main` at c449165, measured from a clean
checkout. **Load average 7–15 during the run** (other sessions building), so wall times carry more
noise than usual; allocation and syscall counts do not, and are what this reading leans on.

**No instruction counts this time.** CachyOS ships its x86-64-v4 glibc, and the dynamic loader
itself (`ld-linux-x86-64.so.2`, `_dl_start`) uses AVX-512, which Valgrind 3.25 cannot decode: every
dynamically linked program dies with SIGILL before its first instruction (`valgrind --tool=none
/usr/bin/true` reproduces it). The callgrind pass collected nothing (`runs/2026-10-14/callgrind/`
keeps the logs). Attribution below comes from `perf record`, `strace` and `heaptrack`; a callgrind
ratchet still works in CI, whose Ubuntu glibc is generic.

## 1. What is worth fixing, in order

### 1.1 `project.remove` copies the whole store while holding the store lock

- **Cost:** in the fixture 451 µs → **7.84 ms** since 10-07 (CPU 558 µs → 7.69 ms, 17×), growing
  over consecutive removals (p50 22 ms over 200 in a row). On a copy of the real 260 MB store, the
  same SQLite online backup takes **142 ms warm, 453 ms cold**. That is 9–28× the engine's 16 ms
  "store lock over budget" line.
- **Where it goes:** `backup_before` (`handlers/workspace.rs`) runs `store.backup_with` inside
  `ctx.read(…)`, which takes the global store lock; under it, `backup_to` (`store.rs`) opens a new
  file, copies every page, and `prune_backups` opens each kept backup to read its project list
  (cheap: 0.5 ms each). `perf` puts 14 % of the fixture's samples in `sqlite3_prepare` for those
  opens; on the real store the page copy dominates.
- **Why it matters:** the lock serializes every request — the session list the sidebar reruns,
  terminal scrollback reads, every agent's `guardrail.gate`. A project removal freezes the whole
  app for a third of a second on this machine, longer on a slower disk or a bigger store.
  `Unlocked::read`'s own doc comment says to keep that closure to plain queries.
- **Fix:** take the backup from a second, read-only connection to the store file opened in the
  unlocked phase — WAL readers do not block the writer and see a consistent snapshot — so the
  store lock is never held for the copy; prune outside it too. The ordering guarantee (backup
  before removal) is unchanged: the unlocked phase finishes before `finish` runs.
- **Expected:** lock held for microseconds; `project.remove` wall unchanged for the caller.

### 1.2 The store is 260 MB, and 85 % of it is hook audit rows nothing prunes

- **Cost:** `~/.local/share/relay-v4/dev/store.db` is 260 MB: the `audit` table 160.6 MB plus
  ~49 MB in its eight indexes. 153 105 rows since 2026-09-05; **94 % are two ops agents' hooks call
  on every tool use**: `guardrail.gate` (64 702 rows, 69 MB) and `session.report` (79 382 rows,
  41 MB), each storing the full hook payload (~1–1.5 KB, transcript paths included). 5 000–20 000
  rows a day.
- **Where it goes:** every row is an insert into `audit` plus eight index updates under the store
  lock (158 µs for a gate, 83 µs for a report in the fixture). The purge worker (`purge.rs`) trims
  other tables; `audit` has no retention.
- **Why it matters:** every operation proportional to the store pays: §1.1's backup, the upgrade
  backup at each schema bump (260 MB written at startup on 10-13), `PRAGMA integrity_check`,
  `VACUUM`, the page cache (32 MiB, an eighth of the file) and the 256 MiB mmap window, which the
  file now exceeds.
- **Fix (needs a decision — what history to keep):** a retention rule for hook rows in the purge
  worker (e.g. drop `guardrail.gate`/`session.report` rows older than 30 days, keep refusals and
  holds); or store a hash and a summary for those two ops instead of the full payload. Then a
  one-time `VACUUM` (or `auto_vacuum=INCREMENTAL`) to give the space back.
- **Expected:** the store back under ~50 MB and holding; §1.1's copy proportionally faster even
  before its fix.

### 1.3 Six GTK pages repaint every frame while nothing changes

- **Cost:** at rest (8 s windows, nothing happening), settings 30 wakeups/s and 0.6 % CPU,
  dashboard 60/s, skills 64/s, notifications 68/s, devices 72/s, palette 126/s and 1.6 %, against
  1–8/s on agents, notes, modules, board. `GDK_DEBUG=frames` logged ~900 frames on devices and
  notifications against 11–20 on the quiet pages: the frame clock is running at the display rate.
- **Where it goes:** something on those pages animates forever. Candidates from the code: the
  mirror card's `gtk::Spinner` (`mirror.rs`, devices) and the skills page's spinner
  (`tools_market.rs`) spinning with nothing loading; for settings, dashboard, notifications and
  palette, not yet attributed — the next step is the Inspector's "Show Graphic Updates" on each.
- **Why it matters:** a minute on one of those pages is ~4 000 frames for nothing; laptop battery
  and, with the game you are playing, a CPU core that never sleeps.
- **Fix:** stop spinners when their load finishes or the page unmaps; no endless tick callbacks
  or `infinite` CSS animations without a visible reason (`perf-gtk` §9).
- **Expected:** every page at rest below 5 wakeups/s and 0 % CPU.

### 1.4 `session.close` checks the checkout twice, and the fixture makes git read every file

- **Cost:** 18.6 ms → 79.5 ms (CPU 2.8 → 3.5 ms); `session.close.created` 8.1 → 39.0 ms. Per close,
  unlinks are unchanged (1 534, the checkout removal), but there are ~7 000 more `openat`/`read` and
  ~13 000 more `newfstatat`.
- **Where it goes:** e806990 ("closing or removing a checkout no longer loses work") runs the
  uncommitted-work check before *and* after the kill — two `git status` (one with `--ignored`) per
  checkout each time. The fixture's checkouts are seconds old, so their index is "racy" and git
  re-reads every file instead of trusting stat data.
- **Verdict:** the work, chosen for safety, and unlocked. On real checkouts older than a second
  git compares stat data. Low priority: skip the second check when the checkout's index and
  directory mtimes did not move since the first.

### 1.5 The GTK client builds everything at startup

- **Cost:** 320–610 ms of CPU in the first two seconds, ~178 MB RSS, 17 threads.
- **Where it goes (from code):** `Ui::build` constructs every page (and every Money, Arbiter, Avex
  and Threads page), installs fonts and icons, and presents the Notes window before connecting; on
  connect ~20 reads go out one after another.
- **Fix:** build pages on first show; batch the connect reads. Measure launch → first frame →
  interactive first (the harness has no first-frame mark yet).

## 2. Looked at and fine

- **`usage.get`** on the real home (478 session files, 4.0 GB): 2.9 ± 0.4 ms against 1.6 ± 0.2 ms for
  `bus.ping` through the CLI — ~1.3 ms of work, unlocked.
- **Heap growth in the soak** (18.9 → 27.7 MiB over 20 000 ops) **plateaus**: 27.83 MiB at 36 000,
  27.93 MiB at 54 000. A cache filling to its cap (the 16 MiB gix object cache from the 09-20 fixes
  matches the jump in starting heap), not a leak.
- **The sidebar** does not rebuild on every `session.changed` (PLAYBOOK lead 7 was wrong): a
  signature over registry, folding, filter and lamp counts guards it; the per-event cost is one
  JSON serialization of the project list.
- **The engine at rest**: 0 % CPU, 3 wakeups/s with six quiet sessions; restart 11 ms; CLI calls
  1.5 ms.
- **`file.restore`** 35 → 118 µs and 89 → 1 634 allocations (gated restore probes); still cheap.
- Most other ops moved ±20–50 % in wall time with flat allocations — the load average, not code.

## 3. Not measured
