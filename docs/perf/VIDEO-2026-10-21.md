# Videos written as code: the agent's loop and a render (2026-10-21)

The Video plugin is new (D167, `docs/VIDEO.md`), so this is a reading, not a before and after. The
journey that matters is the agent's: it edits a file, then asks to see the result; the time from
`video.check` or `video.still` to its answer is what it waits on, every iteration. The person's is
opening a video and pressing Play, and rendering a preview.

AMD Ryzen 7 9800X3D (16 threads), 32 GB, CachyOS 7.2.9, Node.js 26.11.1, Remotion 4.0.534 with its
Chrome Headless Shell. The engine in the dev profile (optimized + debuginfo); the worker and
Chrome are what they are in any build. Load average 7–24 while measuring (other agents building
beside it), so the spread between runs below is mostly the machine's.

## What each step does

| Step | Work |
| --- | --- |
| First check | starts the worker (Node and its modules), bundles the video (webpack, its cache warm from earlier bundles of other videos), typechecks it (a new TypeScript service), opens Chrome and lists the compositions |
| Check, nothing changed | the bundle is kept (the folder's fingerprint is unchanged), the service rechecks only changed files, the browser is open |
| Still, one frame | `selectComposition`, one `renderStill` with the probe, the checks in the engine |
| Sheet of six | six `renderStill`s at 480 px, decoded, checked, laid out and encoded as one PNG |
| Still after an edit | the bundle rebuilt (warm webpack cache), then one frame |
| Preview render | `renderMedia` at half size, CRF 28, H.264 |

## Against the budgets

An agent iterates in seconds, not milliseconds: the 1 s threshold is the one a person feels while
watching it work (PLAYBOOK's journeys). A still after an edit (1.2 s) and a sheet (1.2–1.5 s) sit at
it; a check with nothing changed (0.1 s) and one frame (0.4 s) well under it. The first check of a
session (4–7 s) pays the worker's and the browser's start once; the worker then stays for ten idle
minutes. A preview renders faster than it plays (a 6 s video in 3.8–6.3 s).

## Fix: the worker warms while the agent writes

The first check's split, driving the worker alone with a fresh process (runs 2 and 3; run 1 had
webpack's cache cold): the worker starts in 0.12 s; its first check takes 1.7 s, 0.9 s of it the
bundle and the rest a cold TypeScript service and Chrome starting. An agent spends tens of seconds
writing between `video.create` and its first check, so `video.create` now has the worker check
the starter in the background (nothing recorded): the browser is open and the bundler's and
TypeScript's caches are warm by the time the agent asks.

`video_e2e_first_check_after_writing` (ignored): a fresh engine, `video.create`, 8 s of writing, an
edit, then the timed `video.check`. Three runs each, same machine, load average 22–28:

| | run 1 | run 2 | run 3 |
|---|---:|---:|---:|
| before | 6,960 ms | 9,796 ms | 6,078 ms |
| after | 2,318 ms | 2,118 ms | 1,927 ms |

## Leads

- A still after an edit is mostly the rebundle. Remotion's webpack bundle of a small video takes
  0.7 s warm; esbuild alone, or rspack (Remotion's `enableRspack`), are the candidates.
- No ratchet yet: these are wall-clock times dominated by Chrome and webpack, noisy under load. A
  deterministic proxy (bundles built per still, browser launches per session) is the place to start.
