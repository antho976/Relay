# Fixes from the 2026-10-14 baseline

What was changed after `BASELINE-2026-10-14.md`, measured with the same harnesses on the same
machine (dev profile; load average 7–15, so each engine figure is the median of runs taken back to
back with and without the change). Section numbers refer to the baseline.

The during-a-removal row needed two changes, not one. Moving the backup out of `ctx.read` into
`Store::backup` (which locks one 4 MB batch at a time) took the p50 from ~20 ms only to 14 ms: the
batch loop gave the lock up with `yield_now`, and since the mutex is not fair it won the lock back
before the woken request ran, so a request waited out several batches. Sleeping 1 ms off the lock
between batches hands it over: 0.35 ms.

The client harness had two faults this cycle exposed, both fixed:

- **The at-rest window caught GTK's cursor blink.** A page that focuses a text field draws at the
  frame rate for 10 s after the last input; the window started at 2 s. It now starts after
  `--quiet-after` (10.5 s). A `settings.ini` turning the blink off does not work: the desktop's
  settings portal overrides it.
- **Wakeups went negative** when client threads exited inside the window, since their switches left
  the sum. Only threads alive at both ends are counted now.

## What changed, file by file

- `crates/relay-core/src/handlers/workspace.rs` — `backup_before` calls `Unlocked::backup_store`
  instead of running `Store::backup_with` inside `ctx.read`.
- `crates/relay-core/src/engine.rs` — `Unlocked::backup_store`: `Store::backup` from the unlocked
  phase, or `backup_with` through the held transaction when the op runs nested inside a handler.
- `crates/relay-core/src/store.rs` — `Store::backup` pauses 1 ms off the lock between batches
  (`BACKUP_STEP_PAUSE`) instead of `yield_now`.
- `crates/relay-core/examples/perf.rs` — new scenario `path.session_list.during_project_remove`,
  with 64 MB of ballast so the copy is long enough to land a request inside.
- `apps/relay-native/src/app.rs` — `spinner()`: a `gtk::Spinner` that starts on map and stops on
  unmap. Used by `tools_market.rs` (Skills, Plugins), `threads_view.rs` (Working…, tool steps),
  `agent_menu.rs` (launch progress) and `arbiter_pages.rs` (backtest).
- `scripts/perf/native-baseline.py` — `--quiet-after`, per-thread wakeup deltas.

`cargo test` (1 238 passed), `cargo clippy --all-targets -- -D warnings` and `cargo test -p
relay-native` (78 passed) are clean. The client change was built and measured on the measuring
machine (GTK 4.24.1), inside a headless compositor.

## Guardrails added

- `path.session_list.during_project_remove` — the request's latency while a removal copies the
  store; anything above a few milliseconds means the copy holds the lock again. The harness reports
  in how many iterations the removal was still running (`overlap`: 20 of 20).
- The client harness's at-rest window now reads 0.1–0.5 wakeups/s on every page, so a page that
  keeps the frame clock running stands out at ~60.
