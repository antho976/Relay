# Fixes 2026-10-24: the desktop dev space, from the survey's perf leads

The 2026-10-24 survey (`native-dev.md`) listed PLAYBOOK §5 native leads 8, 10, 11, 13 and 15 as
open, plus smaller costs on the session-event path. Each was measured before anything changed;
three moved, one was measured and needs no change, one is measured and handed on, one could not
be attributed.

Machine: Ryzen 7 9800X3D (16 threads), 30.5 GiB RAM, rust 1.99 (Arch), GTK 4.24.1, **dev
profile** (`opt-level` 1, dependencies at 3). The client ran inside a private
`kwin_wayland --virtual` (1440×900) against a disposable engine with fake providers: the fixture
of `scripts/perf/native-baseline.py` (one project, 201-file repository, six live sessions).
Other sessions were building on the machine throughout, so wall times are noisy; the request
counts, syscall counts and instruction counts are the steadier numbers. Raw runs:
`runs/2026-10-24-devspace/<row>/` (`report.md`, `native.json`).

## What the harness gained

`scripts/perf/native-baseline.py` grew rows for each lead, each runnable alone:

| flag | row | the number |
|---|---|---|
| `--hidden-only --hidden-seconds 310` | agents page minimized 3 s in (the compositor reports `SUSPENDED`), and the same window left on screen | requests the client sends, by op (`RELAY_NATIVE_COUNT_CALLS`, counted in `client.rs`), CPU and wakeups |
| `--events-only` | Code page while 100 files change, 50 ms apart | `stat`/`readlink` calls on the GTK thread (client under `strace`, main thread only) |
| `--burst-only` | Agents page while 200 `session.update` rows arrive (`RELAY_PERF_BURST_GAP`, default 20 ms) | user-space instructions on the GTK thread (`perf stat -t`), over an idle window |
| `--board-tasks 400,2000 [--board-profile]` | three cold launches per size (saved layout cleared, so the board is not mounted at startup), board opened six times each | navigate → first card drawn and laid out (`RELAY_NATIVE_TIME_PAGE`; a tick callback sees it one frame late at most) |
| `--calls-page code` | three launches on the Code page | requests from launch to 10 s, by op |
| `--connect 200` | 200 `bus.ping` on the shared connection, 200 on a connection of their own | round trip, client side |

`perf record` needs `-e cycles:u --call-graph fp --user-callchains` under
`perf_event_paranoid = 2` (plain `-g`, and `-F` above 999 with `-g`, are refused).

## Lead 11 — work while the window is hidden: fixed

Periodic work asks `Ui::later_if_hidden` first and, while the compositor says the window is not on
screen, is noted instead and run once when it shows (`Ui::catch_up`): the 5-minute drift fetch,
the 30 s usage clock (labels and card), a wallpaper turn. Resources skips its 2 s redraw while
hidden. The drift tick also stopped reading `worktree.drift` twice: the fetch's own `git.changed`
reads it.

| 325 s counted | before | after |
|---|---|---|
| minimized | 4 requests: `git.fetch` 1, `worktree.drift` 2, `worktree.list` 1 | **0** |
| on screen (the drift tick) | `git.fetch` 1, `worktree.drift` 2 | `git.fetch` 1, `worktree.drift` 1, `worktree.list` 1 |

CPU at rest was already ~0 % with 0.2 wakeups/s either way: the cost removed is the fetch (a `git`
subprocess and the network) every 5 minutes and a card redraw every 30 s nobody sees. The start
screen's tick callback needs nothing: GTK delivers no frames to a suspended window (12 frame-log
lines in the whole 330 s minimized run).

## Lead 10 — `canonicalize` on the GTK thread: fixed

`Editor::concerns` resolved up to three paths per `file.changed`, each a walk of `lstat`/`readlink`;
checkout roots are now resolved once and cached for 30 s (`editor::canonical`), as is the root in
`links_to_folder`.

| Code page, 100 files changed | before | after |
|---|---:|---:|
| `stat`/`readlink` calls, GTK thread | 272 | **4** |
| per change | 2.7 | 0.04 |

On this local NVMe each was microseconds; the point is the slow or network mount, where each was
a stall of the thread that paints.

## Session events — fixed in part

Every `session.changed` rebuilt the status bar's counts and serialized every project and workspace
to hash the sidebar. Now the counts are redrawn only when blocked/live/parked change, and the
registry is hashed once per change to it (`Sidebar.registry`).

| GTK thread, 200 `session.changed` (8 s window) | before | after |
|---|---:|---:|
| user-space instructions | 321.7 M | 94.1 M |
| per event, over idle | **1.61 M** | **0.47 M** (−71 %) |
| task-clock | 215.7 ms | 32.6 ms |

Tried and reverted: one reconcile per drain of queued events, yielding to a frame every 16 events
(lead 14). With it 476 k / event, with its kill switch 478 k at 50 events/s; unpaced, 491 k against
493 k. The driver waits for each reply, so events never queued; with no measured effect it went.

## Lead 13 — a socket per lifecycle op: measured, no change

| `bus.ping`, client side, 200 each | p50 | p95 | max |
|---|---:|---:|---:|
| shared connection | 31 µs | 61 µs | 185 µs |
| a connection of its own | 75 µs | 130 µs | 226 µs |

About 44 µs per lifecycle op or stock-photo request, against a 100 ms budget. Not worth a pool.
(`session.repo.add` and `.remove` joined the lifecycle set this round for correctness: a clone on
the shared connection held every other request.)

## The Code page's startup reads: fixed

`prepare_project` refreshed the checkouts and Git status after a tree load for a new project had
already done both. From launch to 10 s on the Code page, three launches: `worktree.list` 4, 4, 4 →
3, 3, 3; `git.status` stays 3–4 (it also follows file events), `file.tree` 3.

## Lead 8 — the board: measured, handed on

Board opening (navigate → first card laid out), cold, three launches each:

| tasks | cold, median | each launch | reopen, median |
|---:|---:|---|---:|
| 400 | **352 ms** | 344, 352, 383 | 7 ms |
| 2 000 | **577 ms** | 570, 577, 751 | 12 ms |

The budget is 100 ms at 400 tasks: the first opening of a run is 3.5× over it; later openings are
fine. Sampled at 2 000 tasks, the time is widget construction: libgtk 35 %, libgobject 19 %
(`g_object_ref`/`unref` alone 9 %), libc 14 % (malloc and free), libglib 9 %, Pango and HarfBuzz
9 %, Relay's own code 5.5 %. It is the card-per-task build the lead names (each card a dozen
widgets and five controllers, Done included). The fix is structural — a `GtkListView` for the
list view and lanes, or the Done lane folded and built on demand — and `board_view.rs` was being
revamped by another session as this was measured, so it is left as the next step with these
numbers to beat.

## Lead 15 — CSS: not attributable here

GTK 4.24 on this machine ships without symbols, so the profile names libgtk's hot addresses but
not whether they are style recalculation. sysprof is installed; attribution needs GTK's debug
symbols (debuginfod or a debug package) first. Nothing was changed.
