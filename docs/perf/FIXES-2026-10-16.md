# Fixes 2026-10-16: a new session's first build

A new session gets a worktree of its own, and its first `cargo test` used to compile everything:
every third-party dependency, then the project's own crates. Each worktree also kept its own copy
of those dependencies on disk. On this machine the session worktrees' `target/` directories added
up to about 800 GB (231 GB for one), with 263 GB of the disk left free.

`crates/relay-core/src/build_seed.rs` now copies the project's prebuilt third-party dependencies
into a new session's worktree as a copy-on-write copy. The first build there compiles only the
project's own crates.

Machine: 16 cores, 30 GB, `/home` on btrfs (`compress=zstd:1`), rust 1.99.0 (Arch), dev profile
(`opt-level` 1, dependencies at 3), the headless default members unless a row says otherwise.
Peers were building throughout, so the load average ran from 13 to 46; each pair below was taken
back to back, and the spread between pairs is that noise.

## Before and after

| journey | cold | seeded | change | notes |
|---|---:|---:|---:|---|
| first `cargo test --no-run` in a new worktree (pair 1, load not recorded) | 148.1 s | 72.0 s | −51 % | seeded from a peer's `target/`, local crates' units removed by hand |
| first `cargo test --no-run` (pair 2, load 18–35) | 126.5 s | 70.4 s | −44 % | seeded by `build_seed` |
| the same, a second seeded worktree (load 14) | – | 75.4 s | | |
| then `cargo clippy --all-targets` | 17.5 s | 13.6 s | −22 % | |
| then `cargo build -p relay-native` (GTK) | 71.7 s | 40.7 s | −43 % | |
| all three in sequence | 215.7 s | 124.7 s | −42 % | |
| the copy itself, at session create | – | 0.64–0.73 s | | `cp --reflink=always`, on the seed's own thread |

What is left after seeding is the project's own crates: 9 compiled, 260 fresh
(`cargo test --no-run -v`). They are rebuilt on purpose, see below.

Copying *everything*, local crates included, gained nothing: 73.3 s against 72.0 s for
dependencies only (pair 1). The checkout gives every source file a fresh timestamp, so Cargo
rebuilds the local crates either way. Copying them is also the one part that could be wrong (a
local crate judged fresh by timestamps, or `relay-core`'s `build.rs` embedding plugins by absolute
path), so the seed never carries them.

## The seed's own cost

| | first build (empty staging) | rebuild (staging warm, new commit) |
|---|---:|---:|
| `cargo test --no-run` | 157 s | 100 s |
| `cargo clippy --all-targets` | 36 s | 14 s |
| `cargo build -p relay-native` | 137 s | 39 s |
| total | 340 s | 160 s |

The seed builds in the background at nice 10. A rebuild happens only when a new worktree's
`Cargo.lock` or `rustc -vV` differs from the current generation's, and the new worktree copies the
old generation in the meantime, since most of its dependencies are still fresh. Most of a rebuild
is the local crates, which the seed compiles only because Cargo has no stable "dependencies only"
build.

Disk: `staging/` is 31 GB apparent and each generation 23–25 GB apparent, but they share extents.
`df` fell by about 17 GB over the first build, with peers writing at the same time. Two generations
are kept; a copy in a worktree costs nothing until one side rebuilds a file.

## How it stays correct

- **Cargo's fingerprints do the checking.** A dependency whose version, features, profile or
  compiler changed gets a different unit hash and is built fresh, so an outdated seed is slower,
  never wrong. A merged PR is in the worktree's checkout; the seed carries no source.
- **Local packages are never copied.** Their `.fingerprint/`, `build/`, incremental state and
  uplifted outputs are removed from every generation, so a worktree builds them from its own
  source (`prune`, tested).
- **Build-script paths.** A copied build script's `output` names the seed's directory, but Cargo
  rewrites it to the new target's at use. Checked: after seeding, rustc's `-L native=` paths named
  the worktree's own `target/`.
- **Environment.** The seed inherits the engine's environment, which is the one its agents
  inherit, so `env!`-tracked variables match. A seed built under `cargo test` (which sets
  `CARGO_MANIFEST_DIR`) and used from a plain shell rebuilt `ring` and its 6 dependents. That
  mismatch is between the test runner and a shell, not between the engine and an agent.
- **No torn copies.** A build writes only `staging/`; a generation is published by rename and never
  written again, and it is not swept while a copy reads it. A copy is renamed into `target/` with
  `RENAME_NOREPLACE`, so an agent's cargo that got there first keeps its own.
- **Holding cargo.** A new worktree is marked before `session.create` returns. The guardrail
  gate's unlocked phase holds a cargo command that builds (not `cargo fmt`, `metadata` or `tree`) for up to 10 s while its copy lands, inside the hook's own 20 s deadline. If there is no
  seed yet, it refuses with `build.seeding` (hint: `bus.wait` on `build.seed.ready`) while the
  first build runs, for at most 30 minutes. A burst of new sessions then shares one build instead
  of compiling the same 260 crates once each. Waiting worktrees are served after the first step,
  and an agent's other commands are not held.
- **A failed or panicking build** still ends the build: its waiting worktrees are released, or
  served from the current generation if one exists, so nothing stays refused until the hold runs
  out.
- **Off switch.** If the filesystem cannot reflink (a one-file probe), nothing is built or copied;
  a real copy would be ~28 GB. `RELAY_BUILD_SEED=0` in the engine's environment turns it off.

## What changed, file by file

- `crates/relay-core/src/build_seed.rs`: new. The seed (export, steps, publish, prune, sweep),
  the copy into a worktree, the in-process state of copies and waits, the gate's hold, and unit
  tests for the cargo detector, the pruning, the metadata reader and the holds.
- `crates/relay-core/tests/build_seed.rs`: end to end on a one-crate workspace (skips without
  reflink, as CI's ext4 does), plus an `--ignored` test that seeds a real checkout; the readings
  above came from it.
- `crates/relay-core/src/handlers/session.rs`: `session.create` with a new worktree calls
  `seed_new_worktree` after the checkout, in the unlocked phase.
- `crates/relay-core/src/handlers/guardrail.rs`: the gate's read phase calls `build_seed::gate`
  for exec commands.
- `crates/relay-core/src/engine.rs`, `lib.rs`: the `build_seeds` state.
- `crates/relay-core/src/providers.rs`: agents are told about `build.seeding` and
  `build.seed.ready`.

## Not measured

- A real burst of 5–6 sessions with no seed. The hold is unit-tested; the wall-clock of six held
  agents against six parallel cold builds is not.
- The engine path end to end (`session.create` → thread → copy → gate): the parts are tested, but
  this Relay was not restarted on the change.
