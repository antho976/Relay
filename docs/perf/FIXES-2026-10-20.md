# Fixes 2026-10-20: `relay-core`'s tests as one executable

The question was whether lust (github.com/t3dotgg/lust-lang, a Rust-subset compiler with a warm
daemon and a `tcc` backend) would build Relay faster. It cannot build Relay at all: it has no
`async`, no proc macros beyond its built-in derives and no `unsafe` or `extern`, and Relay is
`tokio`, `serde` and `thiserror` derives, `rusqlite` and GTK. The linker was the next suspect,
and it is already LLD (`readelf -p .comment` on a test executable: `Linker: LLD 23.1.1`); mold is
not installed, and Cranelift needs a rustup nightly this machine does not have.

What a change to `relay-core` waited on was its integration tests. Each of the 67 files under
`crates/relay-core/tests/` was its own crate, so every edit to the engine linked the engine 67
times, at ~180 MB an executable.

Machine: Ryzen 7 9800X3D (16 threads), 30.5 GiB RAM, rust 1.99 (Arch), dev profile (`opt-level`
1, dependencies at 3, line tables only), 8 jobs, LLD. Peers were building throughout: the load
average during the runs was 7–28, so wall times are noisy and CPU seconds are the steadier
number.

## The change

- `crates/relay-core/tests/all.rs` declares 60 of the files as modules (`#[path = "x.rs"] mod x;`)
  and links them as one executable. No test file moved or changed: through `#[path]`, a file's
  own `mod common;` still finds `tests/common/`, so it builds alone or there.
- The 7 files that change process-wide state stay executables of their own: `money` (`PATH`),
  `phase12` (`set_current_dir`), `usage_source` (`HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`),
  `transcript` (`CLAUDE_CONFIG_DIR`), `store`, `integration_registry` and `task_edges`
  (`RELAY_V3_SESSIONS_JSON`). Inside one process, their `set_var` would reach every other test.
- `autotests = false` and a `[[test]]` per executable in `Cargo.toml`. A file in neither place
  would be skipped without a word, so `all.rs` has `every_test_file_is_built`, which fails with
  what to add (checked with a probe file).
- The `--ignored` run lines in `build_seed.rs` and the `design*.rs` measurements now read
  `--test all -- <file>:: --ignored`.

## Before and after

`touch crates/relay-core/src/lib.rs; cargo test --no-run -p relay-core`, the two layouts
alternated with an untimed build after each switch, three rounds each (`runs/2026-10-20-tests/
journey.py`, `journey.txt`). Peak RSS is the sum over every `rustc` and linker process working in
the checkout, sampled every 0.5 s (`runs/2026-10-18-disk/rss-sampler.sh`).

| | 67 executables | `all` + 7 | change |
|---|---:|---:|---:|
| wall time | 44.0 s (43.6–51.7) | 13.0 s (12.3–17.0) | −70 % |
| CPU time (user + sys, every child) | 74.9 s (74.3–75.9) | 18.0 s (17.5–18.2) | −76 % |
| written per rebuild | 68 executables, 12.5 GB | 9 executables, 1.7 GB | −86 % |
| peak RSS, compilers and linkers together | 5.2 GB (4.9–5.7) | 5.1 GB (4.7–5.4) | none |

Wall time follows the load (14–45 here); CPU time does not, and moved the same way. An earlier
set of three alternated rounds gave 48.0–51.8 s against 10.2–30.4 s wall and 73.8–74.7 s against
17.8–19.2 s CPU. Peak memory did not move: 8 jobs at a time either way, and a merged link holds
about what one of the old ones did (1.2 GB at most, both layouts).

Running the tests (`cargo test -p relay-core`, already built): 1 118 tests in 69 executables
took 72.7 s of test time; the same 1 118, plus the new guard, in 10 executables took 46.1 s,
since the 60 files' tests now share one pool of test threads instead of running one executable
after another. `all` passed five runs in a row (633 tests, 7 ignored); 42–66 s each, by the load.

What it does not help, measured the same way, two rounds each:

| `cargo clippy -p relay-core --all-targets` after the touch | 67 crates | `all` + 7 |
|---|---:|---:|
| wall time | 6.8 s, 12.9 s | 9.9 s, 14.1 s |
| CPU time | 10.2 s, 12.6 s | 7.4 s, 9.5 s |

Checking does not link, and one 27 000-line crate is type-checked on one thread where 60 small
ones ran side by side: about 27 % less CPU, and the wall time no better, maybe 1–3 s worse (too
few rounds under this load to say).

## Where the rest goes

`cargo test --no-run --timings` after the change: the engine's own unit tests (`relay_core` lib
built with `cfg(test)`) take 7.6 s and are the critical path; the lib takes 3.2 s, then `all`
3.2 s, which waits for a job slot while the 7 separate executables build (3.7 s each). Merging
those 7 would let `all` start at once, about 2.5 s off the wall time, but each needs its tests
to stop setting the environment first (pass the path in, as `common`'s git helpers do).

## The guard

`scripts/perf/test-exe-size.py` (CI's "Test executable size") had budgets for 62 executables of
~180 MB: largest 210 MB, all 11 GB. After the change the workspace has 24 executables, 3.0 GB in
all, largest `all` at 223 MB. The budgets are now 250 MB and 3.5 GB, so a return to one
executable per file (67 × ~180 MB) fails CI.
