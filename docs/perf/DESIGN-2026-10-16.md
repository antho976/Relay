# Design canvas: first reading (2026-10-16)

The Design view is new, so this is a reading, not a before-and-after: what its journeys cost on
the measuring machine, so the next change to it has numbers to beat. AMD Ryzen 7 9800X3D (16
threads), CachyOS 7.2.9, GTK 4.24.1, dev profile (optimized + debuginfo, what `run.sh` launches),
load average 3.6–6.7. Client figures from `scripts/design-smoke.py perf` inside a headless KWin;
engine figures from that script's socket client and from `cargo test --release -p relay-core
--test design -- --ignored --nocapture` (in process).

## The scenario

One design of 1,721 nodes: 40 phone artboards (390×844, auto layout), each a title and a list of 10
rows of a text, a toggle frame and its knob, all written by one `design.apply` of 1,720 adds as an
agent would. The client opens it, fits it, pans for 240 frames at a fitted zoom and 240 at 100%,
fits again, and drags one artboard across the page.

## Client (relay-native)

| path | median | p95 | max | n |
|---|---:|---:|---:|---:|
| open: `design.get` request, read and decode into the scene | 12.4 ms | | | 1 |
| layout of the page (auto layout, text measured through Pango, cached) | 1.30 ms | 1.55 ms | 1.70 ms | 9 |
| page content render node rebuild | 1.83 ms | | 2.51 ms | 2 |
| frame draw while panning (camera transform over the cached node, overlays) | 0.082 ms | 0.092 ms | 2.77 ms | 486 |

A pan rebuilds nothing: the page's content is one cached render node, and each frame only
transforms it and draws the selection, labels and grid (the max is the first frame, which builds
the node). A drag invalidates layout and content on every motion: about 1.3 ms of layout and 2 ms
of node building per frame for 1,721 nodes, so a drag stays inside an 8.3 ms (120 Hz) frame with
room to spare. At rest the canvas asks for no frames: the only tick callback is the 1.6 s glow
after an agent's change, which removes itself.

## Engine

| path | dev, over the socket | release, in process |
|---|---:|---:|
| `design.get`, 1,721 nodes (reply 191–248 KB) | 5.1 ms | 1.54 ms (store lock held 0.24 ms) |
| `design.apply`, 1,720 adds | 24.4 ms | 11 ms |
| `design.apply`, one text update | 0.21 ms | |
| `design.list` | 0.16 ms | |
| `design.get`, 5,000 nodes | | 3.77–3.85 ms |
| `design.apply`, 1 frame + 499 children | | 3.59–3.81 ms |

`design.get` reads its rows under the store lock and parses them after releasing it; the engine's
CPU per `get` of the big design was 2.2 ms. A first harness read the reply with an unbuffered
`readline` (one `recv` per byte) and saw 82 ms: the harness, not the engine. `design.apply` holds the
lock for its whole list, as every mutation does; 1,720 adds in one call is the largest an agent is
likely to send, and 24 ms of lock is under the 16 ms-per-request budget only for lists of a few
hundred nodes, so the skill tells agents to build a screen per call.

## Guardrails

- `scripts/design-smoke.py perf` prints these timings (`PERF {...}`) and writes them to
  `.impeccable/review/perf.json`; `RELAY_DESIGN_TRACE=1` prints every layout, content build and
  draw of a real session.
- The design suite's ignored timing test (`crates/relay-core/tests/design.rs`) reruns the engine's
  release figures.
- Not yet a ratchet: neither path is in `crates/relay-core/examples/perf.rs`, whose instruction
  counts would gate `design.get` and `design.apply`. Adding them is the next step if the canvas
  becomes a path people wait on.
